1. Introduction						*lsp-introduction*

This plugin talks to a language server over the Language Server Protocol and
brings what the server knows into Vim: what a symbol is, and where it is
defined.

Install it with a plugin manager, with vim-plug for instance: >vim

	Plug 'h-east/lsp.vim'
<
Or put it under a |packages| directory as "pack/*/opt/lsp.vim", which does not
load on its own, and add this to your |vimrc|: >vim

	packadd! lsp.vim
<
Either way, describe the servers to use in |g:lsp_servers|.

Vim frames the protocol messages and matches replies to requests itself, see
|language-server-protocol|, so what is left to the plugin is the conversation
and what to do with the answers.

Changes are picked up with |listener_add()| and sent on as they are made.
When the server asks for incremental updates, |listener-text| supplies the
text of each change, so only the lines that were touched travel.  Writing a
buffer is reported too, for a server that only looks at a file when it is
saved; the text goes along only when the server asks for it.

==============================================================================
2. Requirements						*lsp-requirements*

Vim 9.2.970 or later, with the |+job| and |+channel| features.  That patch is
what lets |listener_add()| ask for the text of a change, which is how a buffer
is kept in step with the server.  Without it, or without the features, the
plugin loads nothing and defines no command.

A language server for the language you work in.  It has to be installed
separately, none is shipped with Vim.

3. Configuration					*lsp-configuration*

							*g:lsp_servers*
g:lsp_servers
		A List of Dictionaries, one per server.  Each entry holds:

		name		Name shown by |:LspStatus|.
		filetypes	List of 'filetype' values the server is used
				for.
		cmd		The command to run, as a List, the way
				|job_start()| takes it.
		rootPatterns	Optional List of file or directory names.
				The first one found from the file upwards
				marks the root of the workspace.  When none
				is found the directory of the file is used.
				Default: [".git"]

		The first entry whose "filetypes" holds the 'filetype' of a
		buffer is the one used for it, so put a more specific entry
		before a more general one.  A buffer whose 'filetype' is in
		none of them is left alone, and nothing of this plugin is
		even loaded for it.

		Example: >vim

			packadd! lsp.vim
			let g:lsp_servers = [
			      \ #{name: 'clangd',
			      \   filetypes: ['c', 'cpp'],
			      \   cmd: ['clangd', '--background-index'],
			      \   rootPatterns: ['compile_commands.json',
			      \		       '.git']},
			      \ ]
<
		One server is started per workspace root rather than per
		buffer, so buffers from the same project share a server.

							*g:lsp_set_omnifunc*
g:lsp_set_omnifunc
		When true, 'omnifunc' is set in a buffer whose server offers
		completion.  Set this to |v:false| to keep whatever the
		'filetype' plugin chose.

		Default: |v:true|

						*g:lsp_completion_timeout*
g:lsp_completion_timeout
		How long to wait for a reply to a completion request, in
		milliseconds.  See |lsp-completion| for why there is a wait
		at all.  A server that has not finished reading the file yet
		takes noticeably longer than one that has, so this needs room
		above what a warmed up server answers in.

		Default: 2000

							*g:lsp_folding*
g:lsp_folding
		When true, the folds are the ones the server works out from
		the syntax.  Off by default: this takes over 'foldmethod' and
		'foldexpr', which are likely set to something already.  See
		|lsp-folding|.

		Default: |v:false|

							*g:lsp_code_lens*
g:lsp_code_lens
		When true, what the server has to say about a line is shown
		above it, such as how often something is used or what can be
		run.  Off by default: this puts text on screen that the file
		does not hold.  See |lsp-code-lens|.

		Default: |v:false|

							*g:lsp_inlay_hint*
g:lsp_inlay_hint
		When true, the names and types a server fills in are shown in
		the window.  Off by default: this puts text on screen that
		the file does not hold.  See |lsp-inlay-hint|.

		Default: |v:false|

						  *g:lsp_document_highlight*
g:lsp_document_highlight
		When true, the other places the symbol under the cursor is
		used are marked once the cursor comes to rest.  How long that
		takes is 'updatetime'.  See |lsp-highlight|.

		Default: |v:true|

							*g:lsp_signature_help*
g:lsp_signature_help
		When true, the signature of the call being typed is shown on
		its own.  Set this to |v:false| to only ask for it with
		|:LspSignature|.  See |lsp-signature|.

		Default: |v:true|

4. Commands							*lsp-commands*

The server ~
								*:LspStart*
:LspStart	Connect the current buffer to the server for its 'filetype'.
		This happens on its own when a buffer is opened, the command
		is for a buffer whose 'filetype' was decided later.
								*:LspStop*
:LspStop	Shut down every running server.  A buffer is connected again
		when it is opened again.
								*:LspStatus*
:LspStatus	List the running servers, whether each one finished starting
		up, how many buffers it has, and how many diagnostics are
		known for the current buffer.
								*:LspLog*
:LspLog		Open a scratch buffer holding what the server for the current
		buffer has logged, which is where one explains why it is
		unhappy.  A server logs in two places and both are shown,
		under a heading each: what it sent as "window/logMessage" and
		what it wrote to its standard error.

		What a server sends as "window/showMessage" is not kept here;
		that one is meant to be read at once and goes to the message
		line as it arrives.  So does what a server says it is busy
		with, such as indexing a project.

Asking ~
								*:LspHover*
:LspHover	Ask the server about the symbol under the cursor and show the
		answer in a popup.  The popup closes when the cursor moves.
								*:LspSignature*
:LspSignature	Show what the call the cursor is in takes, in a popup.  See
		|lsp-signature|.

Jumping ~
							*:LspDefinition*
:LspDefinition	Jump to the definition of the symbol under the cursor.  When
		the definition is in another file it is opened in the current
		window.
							*:LspDeclaration*
:LspDeclaration	Jump to the declaration of the symbol under the cursor, which
		in C is where its prototype is rather than where it is
		written out.  Otherwise like |:LspDefinition|.
						    *:LspTypeDefinition*
:LspTypeDefinition
		Jump to the definition of the type of the symbol under the
		cursor.  Otherwise like |:LspDefinition|.
						     *:LspImplementation*
:LspImplementation
		Jump to what implements the symbol under the cursor.
		Otherwise like |:LspDefinition|.

Filling a list ~
							*:LspReferences*
:LspReferences	Put every mention of the symbol under the cursor into the
		|quickfix| list and open it.  The declaration counts as a
		mention, so it is in the list too.  A file that is not open
		is read for the line to show, which is also what places the
		column.
						    *:LspIncomingCalls*
:LspIncomingCalls
		Put every place the function under the cursor is called from
		into the |quickfix| list and open it.  An entry names the
		function the call sits in, which is what tells this apart
		from |:LspReferences|: a mention is where the name is
		written, a call is who is doing the calling.

						    *:LspOutgoingCalls*
:LspOutgoingCalls
		Put every call the function under the cursor makes into the
		|quickfix| list and open it.  The places are in this file,
		since that is where the calls are written, and each is named
		after the function being called.

						       *:LspSuperTypes*
:LspSuperTypes	Put the types the one under the cursor is derived from into the
		|quickfix| list and open it.  Only the ones it names itself
		are listed: to go further up, put the cursor on one of them
		and ask again.

						       *:LspSubTypes*
:LspSubTypes	Like |:LspSuperTypes|, downwards: the types derived from the
		one under the cursor.

							*:LspOutline*
:LspOutline	Put the symbols in the current buffer into its location list
		and open it.  A symbol inside another, a field of a struct
		for instance, is shown indented under it.
								*:LspSymbol*
:LspSymbol {query}
		Put the symbols in the workspace whose name matches {query}
		into the |quickfix| list and open it.  What counts as a match
		is up to the server.  An entry names the kind of symbol and
		what it is called rather than showing the line it sits on.
							*:LspDiag*
:LspDiag	Put the diagnostics for the current buffer into its location
		list and open it.  See |lsp-diagnostics|.

Changing the text ~
							      *:LspCodeAction*
:LspCodeAction
:{range}LspCodeAction
		Ask what the server can do about the current line, or about
		the lines in {range}, and put the answers in a menu.  What is
		picked is applied the way |:LspRename| applies its changes.

		The reports on those lines go with the question, so what
		comes back is mostly fixes for them.  An action the server
		would rather carry out itself is handed back to it, and the
		changes it works out arrive the same way a rename's do.
							*:LspRename*
:LspRename [{name}]
		Rename the symbol under the cursor to {name} everywhere the
		server knows of it.  Without an argument the new name is
		asked for, starting from the word under the cursor.

		A file that was not open is loaded so it can be changed.
		Nothing is written: |:wall| is what makes it stick, and an
		|undo| in each buffer is what takes it back.  A server asking
		for files to be created, renamed or deleted is turned down,
		since that is not supported.  The same goes for changes a
		server sends on its own.
							*:LspFormat*
:LspFormat
:{range}LspFormat
		Ask the server to format the current buffer, or the lines in
		{range}, and apply what it answers.  The answer describes the
		buffer as it was when the question went out, so nothing is
		applied if the buffer moved on in the meantime.  A single
		|undo| takes all of it back.

		A server may offer to format a whole buffer without offering
		to format part of one, or the other way around, so one of the
		two forms can work while the other says it is not on offer.

What is shown ~
							*:LspFolding*
:LspFolding	Turn the folds from the server on when they are off and off
		when they are on, and say which it now is.  Turning them off
		puts 'foldmethod' and 'foldexpr' back the way they were, in
		every buffer.  See |lsp-folding|.

							       *:LspCodeLens*
:LspCodeLens	Turn the code lenses on when they are off and off when they
		are on, and say which it now is.  See |lsp-code-lens|.

						       *:LspCodeLensRun*
:LspCodeLensRun
		Run what the lens above the current line stands for.  When
		the line has more than one, a menu asks which.

						*:LspInlayHint*
:LspInlayHint	Turn the inlay hints on when they are off and off when they
		are on, and say which it now is.  Turning them off takes
		away the ones already shown, in every buffer.  See
		|lsp-inlay-hint|.

5. Completion						*lsp-completion*

When the server offers completion, 'omnifunc' is set to "lsp#OmniFunc" in the
buffers it handles, so |i_CTRL-X_CTRL-O| asks the server.  A 'filetype' plugin
has usually put a function working from tags there; the server knows more, so
it takes over, and the old value is restored when the buffer is detached.  Set
|g:lsp_set_omnifunc| to |v:false| to keep the filetype plugin's choice.

Unlike the other requests this one waits for its answer, because a completion
function has to return the matches itself.  |g:lsp_completion_timeout| bounds
how long a keystroke can block that way.  When the time runs out a message
says so and no matches are offered; raise the option if a server needs longer
than that while it is still reading the file.

The kind of an item is shown as the single letter |complete-items| asks for.
What a server marks as a snippet is offered under its label: the placeholders
in it cannot be expanded, and inserting them literally would be worse than
inserting the plain name.

A server is allowed to leave the documentation of an item out and hand it over
only for the item that is actually looked at.  That answer arrives long after
the completion function has returned, so what the item already carries goes
into the info popup at once and the rest is filled in when the reply to
"completionItem/resolve" comes.  Include "popup" in 'completeopt' for there to
be a popup to fill in: >vim

	set completeopt+=popup
<
Adding "popuphidden" keeps the popup out of sight until it has something to
show, see |complete-popuphidden|.  Only the item that is selected is resolved,
and only when its documentation is missing.

An item may ask for more than the word before the cursor, "obj->fie" becoming
"obj.field" for instance, which is all omni completion is able to replace by
itself.  What the server asked for is put in place of what completion did, as
part of the same |undo| step.

An item may also ask for changes elsewhere in the file, an include to add for
the name being completed being the usual case.  Those are applied once the
item is taken.  A single |undo| does not take those back with the word: they
are a step of their own.

6. Diagnostics						*lsp-diagnostics*

A server reports what it thinks is wrong with a file on its own, without being
asked.  What arrives is shown in three ways: a sign in the 'signcolumn' on
every line that has something, a highlight over the text a report covers, and
the message itself on the message line while the cursor is on that line.  A
line without a diagnostic leaves the message line alone rather than clearing
it, so this does not wipe out other messages.

|:LspDiag| collects them into the location list, which is the way to walk
through them with |:lnext| and |:lprevious|.

Every report replaces what the server said before, so the signs and the
highlights follow the file as it is edited.

A report may point at other places that explain it, such as where a name was
declared the first time.  Those follow their report in the location list,
indented and without a type of their own, and can be in another file.

These highlight groups are used.  Each is linked to an existing group and can
be given a look of its own with |:highlight|:

	LspDiagError		sign of an error, |hl-ErrorMsg|
	LspDiagWarning		sign of a warning, |hl-WarningMsg|
	LspDiagInfo		sign of an information item, |hl-Directory|
	LspDiagHint		sign of a hint, |hl-Comment|
	LspDiagErrorText	text an error covers, |hl-SpellBad|
	LspDiagWarningText	text a warning covers, |hl-SpellCap|
	LspDiagInfoText		text an info item covers, |hl-SpellRare|
	LspDiagHintText		text a hint covers, |hl-SpellLocal|

7. Signature help						*lsp-signature*

While a call is being typed the server is asked what it takes, and the answer
appears in a popup next to the cursor with the parameter being filled in
highlighted.  The server says which characters start this, "(" and "," for a
C server; the closing paren ends the call and takes the popup with it, as does
leaving Insert mode.  |:LspSignature| asks at any other moment, and setting
|g:lsp_signature_help| to |v:false| leaves the asking to that command alone.

This works while the completion menu is up as well, which is where
'autocomplete' puts one on every keystroke.  The menu is drawn over popups
(|popup-menu|), so the signature is given a "zindex" above it and goes on the
side of the cursor the menu is not using.

The parameter is highlighted with this group, linked to an existing one and
free to be given a look of its own with |:highlight|:

	LspSignatureActive	the parameter being filled in, |hl-PmenuSel|

What a signature says is the server's business.  A macro is reported as what
it expands to, so a call of a macro wrapping a function shows the function.

==============================================================================
8. Symbol highlight					*lsp-highlight*

Once the cursor has rested on a symbol for 'updatetime', the server is asked
where else that symbol is used in the buffer, and those places are marked.
Moving the cursor takes the marks away again.  Set |g:lsp_document_highlight|
to |v:false| to leave the buffer alone.

Somewhere the symbol is written to is marked differently from somewhere it is
only read, when the server says which is which.  These are the groups, each
linked to an existing one and free to be given a look of its own with
|:highlight|:

	LspHighlightText	a mention, the server not saying more
	LspHighlightRead	where the symbol is read, |hl-CursorColumn|
	LspHighlightWrite	where it is written to, |hl-Visual|

==============================================================================
9. Inlay hints						*lsp-inlay-hint*

A server can name what the file leaves unsaid: the parameter an argument is
being passed as, and the type of something declared without one.  Set
|g:lsp_inlay_hint| to |v:true| to have those shown as |virtual-text|, which is
text in the window that the buffer does not hold: >vim

	let g:lsp_inlay_hint = v:true
<
Only the part of the file on screen is asked about, and again whenever the
buffer changes or the cursor comes to rest.

|:LspInlayHint| turns them on and off without leaving Vim, which is the way
to have a look at them and then be rid of them again.

These are the groups, each linked to |hl-Comment| so the hints stay quieter
than the file, and free to be given a look of their own with |:highlight|:

	LspInlayType		the type of something declared without one
	LspInlayParameter	the name an argument is passed as

10. Folding						*lsp-folding*

A server knows where a function or a comment begins and ends, which is more
than 'foldmethod' set to "indent" or "syntax" can work out.  Set
|g:lsp_folding| to |v:true| to fold by what it says, or turn it on for a
while with |:LspFolding|.

Doing so sets 'foldmethod' to "expr" and 'foldexpr' to a function of this
plugin, keeping what was there to put back when the folds are turned off
again or the buffer is detached.  The ranges are asked for afresh whenever
the buffer changes.

Only whole lines are folded.  A server able to fold part of a line is told
not to bother.

What is folded is what the server says, which is not always what 'foldmethod'
set to "syntax" would have done.  A range ends on the line before the closing
bracket, for one, so that line stays outside the fold.

11. Code lens						*lsp-code-lens*

A server can say something about a line without being asked about that line:
how many places use a function, whether a test can be run from here.  Set
|g:lsp_code_lens| to |v:true| to have those shown above the line they belong
to, as |virtual-text|: >vim

	let g:lsp_code_lens = v:true
<
The whole file is asked about, since the protocol has no way to ask about
part of one, and again whenever the buffer changes.  |:LspCodeLens| turns them
on and off without leaving Vim.

A lens carries a command the server runs on its side, so it is worth acting
on rather than only reading.  |:LspCodeLensRun| runs the one above the
current line; when a line gathered more than one, they are shown side by side
separated by a bar and the command asks which to run.

The text is put in the group LspCodeLens, linked to |hl-Comment| so it stays
quieter than the file.

==============================================================================
12. Limitations						*lsp-limitations*

A code action is asked for by line, never by a range within one, so a server
with something to offer about the exact text under the cursor is not given the
chance to say so.  An action the server wants to carry out on its side is
turned down, as answering that takes a request this client does not serve.

A "textEdit" in a completion item is followed only when it stays within the
line the cursor is on.  One reaching across lines is left to omni completion,
which replaces the word before the cursor and no more.
